结论先说

1. 有办法研究，而且已经做到了。这个游戏的脚本全部封在 thndj.mpq（319 MB，熵值 7.9998 ≈ 全加密，无任何可静态提取的明文）。唯一可行路径是在游戏运行时从它自己的内存里把脚本捞出来 —— 已完成，纯只读。

2. 「变量操控界面」确实存在：就是 RMXP 自带的调试画面 Scene_Debug，屏幕上左边一栏 S[0001-0010]／V[0001-0010]，右边一栏列出每个开关／变量的名字和当前值，可以直接改。

3. 它的键是 F9，不是 Shift+F3。打开前提是先输入作弊码 mikomikomomoko 把 $DEBUG 打开。

4. 在这套版本里，Shift+F3 干的是另一件事：切换「剧情超级跳」（$TEXTSKIP）。Shift+F10 才是控制台 —— 可以现场敲 Ruby 代码改任意变量。

5. 下面的「三分钟实测」能让你自己的眼睛判定谁对，不靠我说。

一、Shift+F3 到底是什么

整套热键的输入分发都在同一个函数里：module Screen → def check_input，它被每个场景的主循环调用。全游戏只有两份实现，后加载的那份覆盖前一份 —— 内存地址更高的那份生效（地址 0x1C5CC690 > 0x1C5795F8）。

# 生效版本 · 关键分支
module Screen
  module_function

  def check_input
    update_panel
    if Input.press?(Input::SHIFT) and ($DEBUG or $内测阶段)
      if Kboard.keyboard($R_Key_F3)
        switch_textskip        # ← Shift+F3：剧情超级跳（仅音效，无界面）
      end
      if Kboard.keyboard($R_Key_F10)
        $scene = Scene_Control.new  # ← Shift+F10：控制台，可敲代码改变量
      end
    else                            # 不带 Shift
      if Kboard.keyboard($R_Key_SNAPSHOT)
        Screen::print               # ← PrintScreen：截图
      end
      if !$DEBUG and $scene.is_a?(Scene_Battle)
        if Kboard.keyboard($R_Key_F3)  # ← F3：2 倍战斗速度
          $game_settings.doublespeed_battle = !$game_settings.doublespeed_battle
        end
      else
        if Kboard.keyboard($R_Key_F3) and $DEBUG
          $scene = Scene_Talents_Test.new if $scene.is_a?(Scene_Map)  # ← F3：天赋测试界面
        end
      end
      if Kboard.keyboard($R_Key_F10) and ($内测阶段 or $DEBUG)
        File.open("script.txt"){|f| eval(f.read) }   # ← F10：执行游戏目录下的 script.txt
      end
    end
  end
end

为什么能确定是这一份生效？因为官方 README 「★基础操作★」里白纸黑字写着 F3：2 倍战斗速度 —— 而这段战斗加速逻辑只存在于上面这一份里，另一份（0x1C5795F8，只有一个 F10 截图）根本没有它。既然 README 描述的 F3 有效，生效的就是这一份，那么同一份里的 Shift+F3 = 剧情超级跳 也就成立。

那为什么记忆中它是「变量界面」？三个最可能的答案

① 记的是 F3（不按 Shift） —— 调试模式下在地图上按 F3 会打开 Scene_Talents_Test天赋测试界面，里面用数字键 1 加天赋点、2 减天赋点、9 重置。这确实是个「数值加减界面」，很容易被记成「变量界面」。

② 记的是 Shift+F10 —— Scene_Control 控制台，标题就是「请在下方框中输入代码，按回车确认」，敲 $game_variables[123]=5 就改掉了变量。字面意义上的「变量操控界面」。

③ 记的是 F9 —— 真正的开关／变量总表，也就是下面那张界面。

三种都通向「能改数值」，唯独 Shift+F3 不通向任何界面。

而且它还能导公共事件：同一个 write_event 方法，第二个参数传公共事件 ID 即走 $data_common_events[soul] 分支。script.txt 已接上这一节（见第五节）。

顺带发现：$DEBUG 一开，还会启动一个「联机调试通道」

脚本里有个 Debuger_Map 类，靠 NetGame.dll（挑战模式的联机层）在 TCP 13666 端口上开 server 或连 client，另一边发过来的 \str[指令] 会被本机执行 —— 原本是用来让作者远程看玩家目录的调试工具（Dir.entries(path)）。

它在读取存档时才被创建（Scene_Title 的「继续游戏」分支里调 initdebug）， 而且入口函数第一行就是 return unless $DEBUG。也就是说：不玩联机、不开调试模式，它根本不会启动。 提一句只是让你知道它存在，不用管它。

四、三分钟实测：自己判定 Shift+F3 的真相

不用信我，用你自己的手。整个流程不存档、不写文件，退出游戏即恢复。

  1. 进游戏 → 打开合成（制作）界面 → 用键盘依次敲 mikomikomomoko。听到一声特别的音效（早苗CV玲），说明 $DEBUG 已开。
  2. 退出到地图，按 F9。预期：弹出左栏 S [0001-0010] / V [0001-0010] 的调试画面 —— 这就是那个「变量操控界面」。用 ←→ 试着改一个值。
  3. 关掉调试画面，按 Shift+F3。预期：只有一声音效，不弹任何界面；此时再按住 Ctrl 走一段对话，会发现对话被瞬间跳过 —— 这就是「剧情超级跳」。
  4. 按 F3（不按 Shift）。预期：弹出天赋测试界面，底部写着「这里是 XXX 的天赋测试界面，确认键为天赋加点…数字键 1 为获得一个天赋点，2 为失去一个天赋点」。如果你记忆里的「变量界面」其实是这个，就是它了。
  5. 按 Shift+F10。预期：弹出控制台，可以输入代码 —— 亲手敲 $game_variables[1] 回车，看它把 1 号变量吐出来。
如果第 2 步真的弹出了变量总表、而第 3 步真的弹出了界面，那说明你的游戏版本和这台机器上这份不一样，请告诉我，我改结论。
反之，如果实测与上面一致，那 shift+f3 那个文件夹的命名就是当年记错了键 —— 内容没错，键位记串了。这很常见，F3／F9／F10 和 Shift 组合在记忆里最容易糊在一起。

F10 到底做了什么（顺便解释一个容易误会的事）

脚本里的作者自留通道是：在游戏目录放一个 script.txt，调试模式下按 F10 就会执行它—— File.open("script.txt"){|f| eval(f.read)}。

按一次 F10，游戏目录会多出七个文件： _dump_variables.txt（编号/中文名/当前值）· _dump_switches.txt（编号/中文名/ON·OFF）· _dump_party.txt（队伍、等级、经验、金钱）· _dump_globals.txt（$DEBUG 等运行时状态）· _dump_common_events.txt（全部公共事件——用游戏自带的导出器写出，这是 F11 控制板所在的那一层，磁盘上任何文件都不含它）· _dump_skills.txt（全部技能：编号/名字/说明）· _dump_done.txt（时间戳，证明跑过）。

⚠️ 只管读、只管新建文本：不写存档、不碰脚本、不碰 thndj.mpq。想收手，把 script.txt 删掉即可。

关键：F10 只“读取并执行” script.txt， 它永远不会去写或修改 script.txt 本身。所以如果 script.txt 的 修改时间变了，那只可能是有人（或某个工具）编辑过它，绝不可能是游戏写的。 —— 出现这种疑问时，先看 _dump_done.txt 里记的时间，那才是“游戏真正跑了导出”的时刻。

试错留档：这四条路都走不通，别再重复

· 容器采样熵 7.9993～7.9994，按 zlib 解压 0 处成功 → 不是压缩，是真加密，没有明文可捞；
· 内存里搜 RPG::System 的 Marshal 原文 0 命中（读到的是 RGSS 自带的类定义脚本，里面写的是 @switches = [nil, '']，即只有空默认值）；
· 日文默认名 スイッチ（Shift-JIS／UTF-8）在全内存只有个位数命中 → 名表数组根本不在常驻内存里；
· 全内存按 GBK 解码 → 3700 万条噪声串（方向错了）。本作运行期文本编码其实是 UTF-8， 改成“定向 bytes.find 多编码签名比对”后才得到干净结果（13 秒扫完 532 MB）。

结论：真名只在那个加密文件里，任何“从磁盘/内存直接读出名字”的思路都不会成功； 唯一干净的路就是让游戏自己导出。

六、方法本身（可复用的部分）

这次的路径对所有同类游戏都通用，记下来：

  1. 先证伪静态提取。对 thndj.mpq 逐 MB 采样算熵（全部 7.9998～8.0000），再全量搜 PNG／OGG／RIFF／ZIP／Marshal／Scripts／ruby 等magic —— 0 命中。结论：容器全加密，没有明文可捞，别再浪费时间。
  2. 确认脚本真的在内存里。RGSS（Ruby 1.8）执行脚本时把每段代码作为 zlib 压缩块 留在自己进程的私有内存中，一直驻留到退出。这是唯一的入口。
  3. 只读捞取。用 OpenProcess(PROCESS_VM_READ) + ReadProcessMemory 扫私有内存，按 (?=[\x78][\x01\x5e\x9c\xda]) 找 zlib 头，zlib.decompressobj() 流式解压，再用可打印性过滤。得到 331 段、4.2 MB 源码。
  4. 按内存地址排序 = 加载顺序。这一步是关键 —— RMXP 允许同一函数被重复定义、后加载的覆盖前面的。不知道顺序就不知道哪份生效，容易得出完全相反的结论（这次正好踩到：两份 check_input 的行为互相冲突）。
  5. 用官方文档交叉验证。README 的「F3：2 倍战斗速度」只有其中一份实现了 → 反推生效版本 → 再读同一份里的 Shift 分支。文档和内存互证，结论才敢下。
  6. 仓库化。脚本、导出工具、分析结果都留在 .workbuddy/data/ 与 .workbuddy/tools/，下次换版本可以重跑对比。
结论来源：运行时内存提取的 331 段脚本 + 官方 README（Ver 1.05）交叉验证 游戏本体零改动 · 全程只读
